# A3 — Local NXR MCP

**Status:** ticket. Depends on A2. Do not implement in the same sprint as the RC.6 canary. This is a local stdio adapter over the operation API, not a new scheduler.

## Packaging

Project `.cursor/mcp.json` starts the server on stdio. Remote HTTP transport is later. One MCP tool per NXR task is out of scope.

## Tools

- `operations_search` finds operations from the A2 catalog.
- `operations_describe` returns parameters, context, and policy.
- `operations_plan` resolves the work before anything runs.
- `operations_start` runs an approved local build, test, or check.
- `runs_inspect` returns durable status and node results.
- `runs_get_logs` returns a bounded log.
- `runs_cancel` cancels a run this server owns.
- `workspace_affected` names the verification work for a change.

`operations_start` does not accept a shell string. It accepts an operation id and an idempotency key. A repeated call with the same key returns the existing run id and does not start another execution. Deployment, fleet activation, and remote build tools are absent. An argument that is not a catalog operation id is rejected. An operation whose effect class is `deploy` or `remote` is rejected by this server.

## Idempotency

`operations_start` stores the key in NXR's run store, not in the MCP process.

- The same key, the same operation id, and the same resolved inputs return the original run.
- The same key with different inputs or parameters is a conflict and does not start a second run.
- An explicit rerun after a source change uses a new execution id.
- A detached or interrupted run is inspected and reconnected before another start is considered.

Restarting the MCP server must not duplicate a running task, because the server does not own the idempotency record.

## Phases

A3.0 exposes search, describe, plan, run inspection, and affected-workspace analysis. It does not start work. A3.1 adds local build and test start, bounded logs, and cancel for operations whose effect is `local-build` or `local-mutation`. `remote` and `deploy` stay rejected.

## Acceptance

The first demonstration is in Lattice. The agent selects the filtered Rust verification operation, receives a failure, reads a bounded log, edits the code, and runs that same task again through the pinned environment. The run ids match `nxr`. Repeating `operations_start` with the same idempotency key does not create a second run. A repeated key with a changed source revision is rejected as a conflict until the caller asks for a new execution id. No remote build and no deploy tool are exposed.
